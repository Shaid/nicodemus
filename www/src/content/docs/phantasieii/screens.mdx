Phantasie II's 6 full-screen `.PIC` pictures, served from
`/assets/phantasieii/atarist/`. Unlike every other format on this site,
**no reference-tool source exists for this one at all** — the third-party
C# tool this project reads for a starting point has no P2 `.PIC` support,
so every offset below came from disassembling the real `START.PRG` and
`PHANT.PRG` from scratch with Capstone. Full byte-level trace:
`docs/phantasie/graphics-formats.md` §10. **These are real decoded pixel
data, not illustrations** — no manual colour correction was applied to any
image below.

Layout is the same ST word-Interleaved-by-2 convention as `.PAT` (see
[.PAT Sprite Banks](../../phantasieii/graphics/)), not Phantasie I's Planar
layout — confirmed the same way `.PAT` was, by rendering both candidate
layouts and checking which produced legible art. What's new here is that
**palette is per-file**, resolved from three separate `Setpalette`
(XBIOS function 6) call sites across two different executables, not one
shared table the way Phantasie I's `.pic` uses its five-slot array.

## Title sequence — `START.PRG`, file offset `0x172`

`START.PRG` (2,567 bytes) is a small bootstrap program, distinct from the
main `PHANT.PRG` game engine, that shows these two images and then chain-loads
`PHANT.PRG` via GEMDOS `Pexec`. No string for `COVER1.PIC`/`COVER2.PIC`
exists anywhere in the 155,785-byte `PHANT.PRG` — only in this small loader.

`COVER2.PIC` (320×135, not a full screen) — the Atari-ST-original credits,
blitted as an animated overlay onto the *bottom* of the title screen. This
isn't a guess: `START.PRG`'s own code advances its screen-buffer pointer by
exactly `0x28A0` bytes (`65` rows) before loading it — `65 + 135 = 200`
exactly completes the screen, leaving `cover1.pic`'s own logotype visible
in the untouched rows above. Both images share one palette, set once
between the two loads.

`PELNOR.PIC` — the in-game town screen, directly comparable in composition
to Phantasie I's own `pelnor.pic` town screen. Its palette is set by a
function called right before the town-entry code path reaches the real
picture-load routine — a different table from the title screen's, and from
the ending-sequence palette below (verified distinct byte-for-byte, not
just assumed).

## Ending sequence — `PHANT.PRG`, file offset `0x23a9e` (the monster/race palette)

`DECOR.PIC` and `FINAL2.PIC` are loaded back-to-back inside one function,
with a `Setpalette` call to Phantasie II's already-confirmed
monster/race palette right after `decor.pic` loads — reusing the combat
palette for the ending art mirrors what Phantasie I's own `decor.pic`/
`final.pic` do, a real repeated authoring convention across both games.

`CROWD.PIC` (320×93, only 3 bitplanes — 8 colours instead of 16) — loaded
immediately after `final2.pic`, inheriting the same palette, but into a
**separate buffer in the executable's own uninitialised BSS memory**
rather than straight to the screen the other five files use. That's a
genuinely different loading path from every other file on this page — the
game likely composites this one in smaller pieces rather than as one flat
blit, though the exact compositing step wasn't traced. Decoded flat as a
single image (as shown here), it's legible as four bands of small
spectator figures with arms raised; see
[Graphics Formats](../../phantasieii/graphics/) for the full evidence trail,
including why 320×93×3bpp was the only candidate shape that didn't produce
a repeated-tiling artefact.
