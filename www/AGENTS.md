## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and
`astro dev logs`.

## Build & asset wiring

This site is a curated, human-readable companion to the repo's Phantasie
reverse-engineering notes, covering all three games (each in its own
`src/content/docs/<id>/` section — see `README.md` § "One module per game"
for how a game's config is fully isolated in its own
`scripts/games/<id>.mjs`, never shared build-script code). Three things are
**generated**, never edited by hand:

- `public/assets/<game>/` (one per game) — copied from the repo's
  `public/assets/<game>` by `scripts/build.mjs`, so the site is
  self-contained. When the source is missing (e.g. in CI, which never has
  the original copyrighted game files), the already-committed copy under
  this site's own `public/assets/<game>` is used instead — that
  committed copy only exists because a previous local build produced it, so
  it must stay committed even though the repo-root extraction output usually
  isn't.
- `public/favicon.png` — either the placeholder this scaffold ships with, or
  generated by `scripts/generate_favicon.mjs` from a real sprite frame once
  some game's `scripts/games/<id>.mjs` exports a `favicon` config (see
  README.md).
- `generated/sidebar.mjs` — the Starlight sidebar, generated by concatenating
  every game's own `src/content/docs/<id>/_sidebar.json`.

`npm run dev` and `npm run build` run `scripts/build.mjs` first, so assets,
favicon and the sidebar stay in sync automatically. Run it manually with
`node scripts/build.mjs`.

A fourth section, `formats`, is **not** a game: it documents the shared
bitplane/palette encoding and the dungeon/scripting engine Phantasie I and
II share byte-for-byte, all three games' data feed into. Its module
(`scripts/games/formats.mjs`) exports `docsOnly = true` so `build.mjs` skips
the asset-copy step for it. See README.md § "Docs-only sections".

### Editing the site

This section covers **wiring**. For **content standards** — page types and
their skeletons, how claims must be evidenced, and the pre-publish checklist —
the account-wide `seer-website` skill carries them (and `WRITING-GUIDE.md`
in this repo carries the same standard, condensed).

- **Curated pages** live in `src/content/docs/<id>/` per game. If this
  project also keeps raw research notes elsewhere in the repo (it does,
  under `docs/phantasie/`), curated pages should summarise that research —
  when a curated page disagrees with the raw notes, the raw notes win. Update
  the curated page, not the other way around.
- **Sidebar order/labels**: edit that game's own
  `src/content/docs/<id>/_sidebar.json`, then re-run the build
  script. Slugs are the content file paths under `src/content/docs/` (a
  game's home page slug is `<id>`, not `<id>/index`).
- **Sprite galleries**: use `src/components/SpriteGallery.astro`, passing
  `manifest`/`assetPath` for the packed-frames atlas to render, and
  optionally `hoverPairs`/`clickChains`/`labels` for hover-swap, click-cycle,
  and display-name behavior. The component has no built-in knowledge of any
  game's data shapes — the calling page builds the `labels` map itself from
  whatever name data actually exists. See README.md for a worked example.
- **Click-to-enlarge**: `src/components/Lightbox.astro` — drop `<Lightbox />`
  once per page, add `data-lightbox` (+ optional `data-lightbox-label`) to
  any `<img>` or background-image-cropped element on that page. See
  README.md and `src/scripts/lightbox.js`'s docblock.
- **Images**: reference copied assets by URL path, e.g.
  `/assets/<game>/amiga/mstr1.png`. Re-run the build script after the
  repo's `public/assets` changes.

### Asset-resync workflow

When a game's upstream extraction changes (new sprites, corrected data, etc.):

1. Regenerate that game's extraction locally (at the repo root:
   `npx tsx tools/extract-game-data.ts --game all --platform all`) so the
   repo's `public/assets/<game>` is current.
2. Run `npm run dev` or `npm run build` in this site — `scripts/build.mjs`
   re-copies the assets and regenerates the sidebar/favicon as needed.
3. Commit whatever changed under this site's `public/assets/<game>`
   (and `public/favicon.png`, if it changed) — that's the mirror CI deploys
   from.

## Known gotchas (multi-agent build sessions)

- **MDX parser bug: a standalone comment line directly before an
  object/array-literal `export const` breaks the build.** Confirmed with
  `@mdx-js/mdx`'s `compile()` in isolation: `export const A = {x: 1};\n\n//
  comment\nexport const B = {y: 2};` fails to parse (`Could not parse
  expression with acorn`, source `micromark-extension-mdx-expression`) —
  but only when the *second* export's value is an object or array-of-objects
  literal; `export const B = [1, 2]` (primitives) is unaffected, and it
  doesn't matter whether the comment is `//` or `/* */`. **Fix**: never put
  a bare comment line immediately before such an export. Either move the
  comment inline on the same line as the opening bracket
  (`export const B = [ // comment`, with any further comment lines moved
  *inside* the array as the first lines after the bracket), or fold the
  explanation into surrounding Markdown prose instead of a JS comment. Astro
  build errors from this only report `line:col`, not the file — worse, in
  this multi-game site the reported `line:col` drifts between builds if
  other games' content files are being edited concurrently by sibling
  agents, since Vite bundles the whole site as one process. If you hit an
  "Expected `,` or `)` but found `:`" or "mdx-jsx:unexpected-character"
  build error with no filename, don't trust the line:col from a full
  `astro build` — instead bisect with `@mdx-js/mdx` directly against each
  of *your own* `.mdx` files (`compile(readFileSync(path, 'utf8'), { jsx:
  true })`, run from inside `www/` so it resolves `node_modules`), which
  reports `e.place`/`e.line`/`e.column` for that one file deterministically.
- **Port collision between concurrent agents' dev/preview servers gives a
  false "images 404" signal.** If another agent already has `astro dev` (or
  `preview`) running on the default port, your own `astro preview` silently
  picks the next port up (logging "Port XXXX is in use, trying another
  one..." to its own stdout/log file, easy to miss) — `curl`/Playwright
  traffic aimed at the default port then hits the *other* agent's
  server/content, which can look exactly like a real broken-asset bug in
  your own pages. Before debugging a "my images/pages don't load" symptom,
  check `ps aux | grep astro` for an already-running server and read your
  own preview command's actual startup log for the port it really bound.
  **Prefer a one-shot `node scripts/build.mjs && npx astro build` for
  verification over starting a dev server** when working alongside sibling
  agents on other games' sections — it avoids both the port-collision trap
  and concurrent writes to the same `dist/` output.

- **This site deploys to a subpath (`base: '/nicodemus'` in
  `astro.config.mjs`), and Astro/Starlight do not auto-prefix hand-authored
  links or images with it — not even inside Starlight's own frontmatter
  fields (e.g. a splash page's `hero.actions[].link`).** Starlight's own
  *generated* chrome (sidebar, pagination, breadcrumbs, favicon) is
  base-aware automatically; anything you typed a path into yourself, YAML or
  JS, is not. **Rule**: in `.astro` components or `.mdx` frontmatter/JS, build
  paths with `import.meta.env.BASE_URL`, but normalize its trailing slash
  first — it is **not** guaranteed to end in `/` (that depends on the
  separate `trailingSlash` config, not on how `base` is written):
  `` const base = import.meta.env.BASE_URL.replace(/\/$/, ''); `${base}/assets/...` ``.
  In markdown/MDX prose *and* in frontmatter YAML link fields, use a
  **relative path** computed from the page's route depth (e.g.
  `../../assets/phantasie/amiga/cover1.png` from a page two segments deep,
  or just `phantasie/`/`assets/foo.png` with no prefix from the depth-0
  homepage), never an absolute `/assets/...` or `/phantasie/...`. **Never use
  markdown `![alt](path)` image syntax for a `public/assets/` image** —
  Astro's markdown image pipeline intercepts that syntax specifically and
  either silently skips base-prefixing (absolute path) or fails the build
  outright with `[ImageNotFound]` (relative path, since it tries to import it
  as a local `src/`-relative asset). Use a raw `<img src="...">` HTML tag
  instead — it passes through untouched in both `.md` and `.mdx`. Full
  writeup with the empirical evidence:
  `~/.claude/skills/seer-website/references/base-path.md`. Before calling any
  subpath-deploy change done, build with the real `base` set and grep
  `dist/**/*.html` (including the homepage) for un-prefixed
  `href="/`/`src="/`.
